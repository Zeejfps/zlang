# Decisions

One line per decision, newest last. The samples are the spec; this file records *why*.

- `todo.tbl`: general purpose (tables, projections, contexts)
- `game.tbl`: ECS (keyed tables, joins, systems)
- `todo_ui.tbl`: declarative GUI (views, state, events)
- `server.tbl`: HTTP server (string keys, optionals, concurrent requests)

## Settled

- Declarations start with a keyword (`table`, `projection`, `context`, `fn`, `let`), so the parser always knows what it is reading from the first token.
- Statements end with `;`. A missing `;` gives a precise error and avoids newline-sensitivity rules.
- Types appear only after `:` or `->`, so `<` in `table<Todo>` never has to be told apart from less-than.
- Values are constructed with named-argument calls: `Stats(total: 1, open: 0)`, `App()`. There is no `Todo { … }` literal, so `{` after an expression always opens a block. Construction, function calls and GUI elements share one syntax, and a missing `required` field is reported as a missing argument. `insert` and `update` take columns as named arguments too: `update(app.todos, id, done: true)`.
- A trailing block attaches only to a call that begins a statement (`row(gap: 4) { … }`). Inside an `if`/`for`/`while` header, `{` is always the body. The parser decides this from position alone and never needs types.
- `..p: T` in a parameter list takes T's fields as named parameters, and `p` is the assembled value in the body. Built-in `insert` uses the same convention, so a function can wrap it (`spawn_rock(world, x: 5.0, y: 5.0)`) without changing how callers write columns. Rules:
  - Spread fields are passed by name only, so column order never becomes part of an API.
  - A field name that appears in two spreads is an error at the declaration.
  - `f(..value)` at a call site passes a whole value.
  - Calling with named fields requires T to be known from the positional arguments: in `insert(world.positions, entity: e)`, `world.positions` fixes T = `Position` before the fields are checked. Generic code passes whole values only, so errors never appear late, at instantiation.
  - There are no prefix ranges (`..5`), so a leading `..` always means spread.
  - There is no overloading.
- Tables are part of the language, not a library. `table Todo { … }` declares a schema (as SQL's `CREATE TABLE` does), and `table<Todo>` is the built-in type of a table of Todo rows, lowercase like `list<T>`. The schema is named for the row, because rows are named far more often (`id<Todo>`, `from Todo`, `..p: Todo`, parameters). The compiler knows every table's columns and keys, and every place a table is read or written. `insert`, `update` and `delete` are built-in operations, so `update` needs no partial-struct type to express "fields left out are unchanged".
- `key` is a column modifier, like `required`: `entity: id<Entity> key;`. The key has a real name and is passed to `insert` by name like any other column (`insert(entity: hero, x: 0.0, y: 0.0)`). Several bindings in one `for` join on key columns, which must have the same type. A table with no key column gets an implicit `id: id<T> key`.
- `id<T>` is the only kind of opaque id: the key of a row in table T, generated by `insert`, compared but never computed with. There is no separate id declaration. An ECS entity is a row in `table Entity {}`, and components key by `id<Entity>`. Spawning is `insert(entities)`, and despawning is `delete(entities, e)`, which also deletes every row in the context keyed by `e`. Keys of other types (`name: str key`) are allowed. `id` is lowercase like `table` and `list`, and since types appear only after `:` or `->`, `id: id<Todo>` never clashes with the column name.
- Deleted ids are never reused silently. Each `id<T>` carries a generation, so a stale id finds nothing (`get` returns empty) rather than a different row. This is needed regardless of what tables do, because ids also live in variables, lists and view state, where no cascade can reach them.
- Columns holding an `id<T>` choose what happens when its row is deleted: `cascade` deletes the referring row, `clear` sets the column empty, and with no modifier the id goes stale. Key columns always cascade. The policy is per column, not per table, because one table can hold several references (`Follows`). Going stale is the default because it costs nothing; `cascade` and `clear` make the compiler keep a reverse index for that column only. Cascades stay inside one context.
- `?T` is an optional T, either a T or `none`. The `?` comes first so the first token of a type says what kind of type it is, and function types need no precedence rule: `?fn() -> int` is an optional function, `fn() -> ?int` returns an optional. Like `<`, it appears only in types.
- Optionals are unwrapped by binding, never by flow analysis: `if let t = x { … } else { … }`, or `let t = x else { continue; };` to bind or leave the block. `x ?? default` supplies a fallback. The bound name is a plain `T`, scoped to where it was bound. There is no narrowing after `if x != none` and no force-unwrap `!`.
- A `for` binding written `t in table by k` matches the row whose key is `k`, instead of joining on the shared key, so a loop can follow a reference (`t in world.positions by h.target`). If no row has that key, the loop skips that combination. Only bindings over a whole table without `by` take part in the implicit key join. Outside loops, `get(table, k)` returns `?T`.
- `_ in table` keeps only rows whose key has a row in that table, and `_ not in table` keeps only rows whose key has none (`for p in world.positions, _ not in world.players`). Both work with `by`. A `not in` binding has no row, so it must be `_`. The filter is part of the query rather than an expression in `where`, so the compiler plans it and counts it as a read directly.
- A `for` binding is read-only unless written `mut`: `for mut p in world.positions, v in world.velocities`. A `mut` binding is a reference, so `p.x += …` writes to the row. A read-only binding behaves as a copy taken when it is bound; the compiler only really copies when a `mut` binding in the same loop shares its table, so it can never see a half-written row. Two `mut` bindings on one table in one loop are an error, because they could be the same row. Outside loops, `update(table, id, …)` writes a single row.
- References exist only as `mut` loop bindings and cannot leave the loop: they cannot be stored, returned or captured by a closure. That makes them safe without lifetimes or a borrow checker, as with Swift's `inout`.
- Inserts and deletes inside a loop are deferred until the loop ends, so a reference never points at a row that has gone.
- A function's reads and writes are collected from its body and the functions it calls (`mut` bindings, `update`, `insert` and `delete` write; everything else reads). Headers do not declare them. The scheduler uses these sets to run systems in parallel when neither writes a table the other uses.

- There are no methods. `.` is only field access, and `::` names something inside a namespace: `strings::strip_prefix(req.path, "/")`, `http::serve(…)`. A module is a namespace, and `use http::{Request, Response};` brings names in unqualified; importing two names that clash is an error at the `use`. The parser knows what `.` means without types or name lookup, every function is declared one way (`fn`), and generic code is just generic functions. Methods may come back later as call sugar.
- `insert`, `update`, `delete`, `get` and `count` are table operations in the prelude, which every module imports; the table comes first: `insert(world.positions, entity: e, x: 0.0)`. When a module defines its own `insert`, `tables::insert` still reaches the built-in. Other namespaces are written out (`lists::count`, `clock::now`).
- A namespace never has the same name as a type or a keyword, so `x::` is never confused with one: `tables::insert`, not `table::insert` (`table` is a keyword); `clock::now`, not `time::now` (`time` is a type). Collection namespaces are plural, as in Go's `slices` and `strings`: `tables`, `lists`, `strings`.
- Calls are not nested as arguments; the inner result goes in a `let` first. This is a style rule for the samples, not a grammar rule.

## Open

1. **Projections:** must a projection come `from` a table, or are free-standing ones (like `Stats`) fine too?
2. **Contexts:** pass them explicitly (`app: App`), or have functions declare them (`fn add(text: str) uses App`) so they are in scope?
3. **Queries:** is `from … where … select …` built into the language, or a library of functions over tables?
5. **Row identity:** is an implicit `id: id<T> key` the right default for a table with no key column, or should that line always be written out?
6. **`required`:** does it mean "no default, must be set on insert"? If so, should fields without a default be required anyway?

### From ECS (`game.tbl`)

7. **Composite keys:** may a table have two `key` columns (a relation like `table Follows { follower: id<User> key; followed: id<User> key; }`)? If so, how do joins pick which key to match?
8. **Optional joins:** a binding that yields `?T`, for "entities with a Position, and their Velocity if they have one" (Bevy's `Option<&Velocity>`). Do we need it, and with what syntax? Left out until a sample needs it.
11. **Hidden access:** a closure called through a variable hides what it reads and writes. Treat such a call as touching everything, or give closure types an access declaration? And should a header be able to declare access, checked by the compiler, for systems that must stay parallel?

### From GUI (`todo_ui.tbl`)

12. **Reactivity:** for views to re-run, the runtime must track which tables and rows a view read. Should tracking be per row or per table, and should it be automatic or declared?
13. **View state:** keep `state` local to a view, or store UI state in tables and contexts as well ("everything is a table")?
14. **Binding:** use `text_input(bind draft)` as shorthand for `value: draft, on_change: fn(s) { draft = s; }`?
15. **Row to projection:** can a `Todo` row be passed where a `TodoLine` is expected, without being converted explicitly?
16. **Trailing blocks:** the parsing rule is settled. Are they allowed only inside `view`, or everywhere (for example `with_lock(m) { … }`)? And can a projection like `Button` be an element directly?
17. **Closures and modules:** `fn(b: bool) { … }` is a placeholder. Namespaces are settled, but not what makes a module (a file? a directory?) or how names are made public.

### From spreads

19. **Spread override:** is `f(..p, y: 5.0)` allowed, with the explicit field overriding (as in Rust's struct update syntax), or is it a duplicate-field error?

### From `id<T>`

21. **`restrict`:** add a modifier that makes a delete fail while something still refers to the row ("can't delete a customer who has orders")? Useful for business data, awkward with deferred deletes in games. Left out until a sample needs it.
22. **Optional chaining:** add `x?.field` (empty if `x` is), or wait until a sample needs it?

### From HTTP (`server.tbl`)

23. **Concurrent requests:** handlers share one context. Does each request run as a transaction, so `follow` can't lose a hit when two requests read `hits` at once, or must the program ask for that (say, an atomic `update(store.links, slug, hits += 1)`)?
24. **Duplicate keys:** what does `insert` do when the key is taken: fail, return an optional, or replace the row? `add_link` checks with `get` first, which races with another request.
25. **Mutable locals:** the sample writes `let mut body`, matching `mut` loop bindings. Are locals read-only unless written `mut`?
26. **Errors:** every failure here becomes a `Response` through `let … else`. Is that enough, or does the language need a result type with propagation?

### From namespaces

27. **Chaining:** without methods, a sequence of steps is a sequence of `let`s. If that gets long in a sample, add a pipe (`x |> f()`) or dot-call sugar for methods?
